# Защита от передачи доступа

## Реализовано в панели и ttmenu

| Механизм | Что действительно ограничивает |
| --- | --- |
| Отдельная запись устройства, отзыв, смена пароля | Распространение общего пароля можно остановить отзывом этой записи |
| Квота и срок, отдельный автоотзыв | Объём и время использования записи; не число людей |
| Одноразовое приглашение с TTL и необязательным IP/CIDR | Получение профиля из указанной сети; не последующее копирование |
| Предупреждения по наблюдавшимся сетям | Сигнал для проверки администратором, без автоматического бана |
| Ограничение BitTorrent | Частичный фильтр выхода TrustTunnel; см. ниже |

Новые ограничения выключены по умолчанию. Существующие пароли, сертификаты и профили не меняются. Транспортный пресет «1 H2 + 1 QUIC» удалён из антишаринга. Его старый API-запрос отклоняется без изменений. Уже заданные технические лимиты автоматически не сбрасываются.

### Наблюдение сетей

Клиенты → Управлять → Антишаринг → Подозрительное использование. В ttmenu: управление клиентами → 19/20, отчёт → 12. Нужны штатные метрики клиентов на localhost.

Окно 5–1440 минут; порог 2–100 наблюдавшихся сетей. IPv4 считается по адресу, IPv6 по /64 либо /128. По умолчанию /64 уменьшает ложные тревоги из-за временных IPv6-адресов. IPv4-mapped IPv6 нормализуется в IPv4.

Endpoint отдаёт один агрегированный IP на логин. Опрос не видит все одновременные подключения и может пропустить короткую сессию. Это НЕ счётчик устройств, НЕ доказательство шаринга и НЕ механизм ограничения активных IP. Смена Wi-Fi/мобильной сети допустима. Даже превышение порога не вызывает Fail2ban, отключение клиента или смену его пароля. Администратор выясняет ситуацию и отдельно отзывает доступ при необходимости.

Наблюдения сохраняются в приватной SQLite-базе: последний образец для каждого IP, не более 256 IP на запись, срок истории до суток. При достижении предела часть истории вытесняется; счётчик может недооценить число сетей. История доступна только администратору. При недоступных метриках интерфейс показывает это отдельно. Работа наблюдения и существующих квот зависит от запущенной панели.

### Выдача профиля

В одноразовом приглашении можно указать внешний адрес получателя или узкий CIDR. Проверяется адрес фактического TCP-соединения с панелью, не `X-Forwarded-For`. За reverse proxy это адрес прокси: не используйте такую привязку как адресную защиту конечного получателя. Несовпадение адреса не погашает токен. Ограничение не защищает от другого получателя в том же NAT и не ограничивает VPN после импорта.

Пустое поле сохраняет обычную одноразовую выдачу. Предпросмотр ссылки не погашает токен. Уже полученный TOML/tt-профиль остаётся копируемым.

## Строгий режим: проект, пока НЕ реализован

Ни IP-лимит на учётную запись, ни криптографическая привязка устройства не включаются этим релизом. Панель явно сообщает `active_ip_limit=false` и `device_binding=false`. Нельзя имитировать их транспортными счётчиками или банами по агрегированному IP.

### Уровень 1: admission-контроль в endpoint

Нужна доработка endpoint перед допуском аутентифицированного туннеля к передаче данных. Она может сохранить совместимость с официальным клиентом, поскольку решение принимает сервер.

1. Одна атомарная таблица на учётную запись для HTTP/2, HTTP/3 и всех поддержанных путей авторизации. Запись связывает ID туннеля, нормализованный исходный IP и эпоху процесса. Разные логины независимы, IP не является глобальной идентичностью.
2. Лимит считает различные активные внешние IP, а не число туннелей или IP назначения. Повторные туннели с уже допущенного IP не расходуют новый IP-слот. Независимый технический потолок защищает ресурсы, но не используется как антишаринг.
3. При превышении отклоняется только новый туннель. Уже работающий владелец не вытесняется. Последнее соединение освобождает IP-слот; RAII/обработчики отмены и исключений предотвращают утечки. Нельзя освобождать слот активного туннеля только по таймеру отсутствия прикладного трафика.
4. Для QUIC учитывается подтверждённый адрес пути. Миграция требует атомарного переноса слота до разрешения данных по новому пути; неподтверждённый UDP-источник не даёт события нарушения для бана. Для мобильной смены сети нужен явный режим handover, а не бесконтрольное вытеснение старого IP.
5. После отзыва/смены пароля закрываются туннели этой записи, а не все пользователи. Режимы: наблюдать, отклонять новые, отклонять + дополнительный временный IP-бан. Неизвестная возможность endpoint блокирует включение строгого режима.
6. Метрики содержат отдельные проверяемые данные: активные IP, разрешённые/отклонённые admissions, причина, версия политики. Панель не восстанавливает эти сведения из единственного агрегированного IP.

Ограничение: несколько людей за одним NAT или через общий промежуточный прокси выглядят как один IP. Серверный IP-лимит не решает эту задачу и не запрещает раздачу интернета через уже допущенное устройство.

### Fail2ban: дополнительная реакция, не источник истины

Предложенные настройки: три подтверждённых отказа `ip_limit` за минуту, начальный бан 60 секунд, максимум 10 минут. Это проектные значения, не включённый jail. Для одного IP допустимы предупреждение вместо бана и исключения администратора.

Событие формирует endpoint ПОСЛЕ корректной аутентификации и отказа admission-контроля. Адрес берётся из проверенного peer endpoint, а не имени пользователя, HTTP-заголовка или присланного клиентом текста. Пароли, TLS-ключи и секреты приглашений в событие не попадают. Отдельный journal/unit, жёстко фиксированная структура, тесты подставленного IP и многострочного текста обязательны.

Действие блокирует только текущий порт TrustTunnel по TCP и UDP для IPv4/IPv6. SSH, HTTPS-панель и другие сервисы не затрагиваются. При смене VPN-порта jail обновляется в той же подтверждённой операции. Нужны ограниченная длительность, список исключений, ручной unban, журнал причин и проверка порядка правил с UFW.

Даже портовый бан отрежет ВСЕ логины за этим IP на порту VPN. Поэтому по умолчанию лучше отказ конкретному туннелю без Fail2ban. Бан не применяется на основании частой смены сети, количества H2/QUIC-туннелей, ошибок TLS сканера или агрегированных метрик. Текущий релиз такой автоматический jail не устанавливает.

### Уровень 2: ключ устройства

Нужны доработки клиента и endpoint. Протокол proof-of-possession нельзя добавить одной настройкой панели.

- При регистрации клиент создаёт ECDSA P-256 ключ в Android Keystore. В строгом аппаратном режиме сервер проверяет attestation-цепочку, challenge, назначение ключа, уровень TEE/StrongBox, доверенные корни и отзыв. Неподдерживаемый аппаратный режим не заменяется молча программным ключом.
- Сервер хранит публичный ключ, ID записи, состояние отзыва и лимит зарегистрированных устройств. Первичная регистрация требует одноразового приглашения/подтверждения администратора. Знания копируемого пароля недостаточно для регистрации второго ключа.
- Авторизация туннеля требует подпись одноразового 32-байтного challenge с коротким TTL. Подпись связывает версию протокола, сервер, учётную запись, device ID, nonce и контекст конкретного защищённого соединения. Нужна защита от replay и переноса доказательства на другой туннель. Один успех не выдаёт долгоживущий копируемый bearer-пароль в обход проверки.
- Все H2/H3 пути обязаны проверять ключ, иначе останется обход через второй транспорт. Legacy-профили отклоняются только для явно переведённых записей. Общий endpoint переводится постепенно после проверки тестовой записи.
- Замена телефона: отзыв старого ключа и новая подтверждённая регистрация. Нет IMEI/Android ID как секрета; закрытый ключ не попадает в TOML, QR или подписку.

Аппаратный ключ мешает перенести профиль на другой телефон, но не делает невозможными tethering, удалённое управление допущенным телефоном или использование его как signing oracle. Комбинация ключа, admission-политики, квоты и отзыва ограничивает злоупотребления, но обещание «никогда нельзя поделиться интернетом» технически некорректно.

### Критерии допуска строгого режима

До реализации и прохождения этих испытаний строгие переключатели должны оставаться недоступны: H2 и H3 вместе; два независимых источника; гонка 100 admissions при лимите 1; один NAT с разными логинами; IPv4-mapped/IPv6; повторное подключение; отмена и авария; QUIC migration; смена пароля; отзыв ключа; replay; неверная подпись; поддельный лог; недоступность панели; перезапуск endpoint; откат без смены пользовательских сертификатов. Нужен и настоящий Android-клиент, не только CLI.

## Ограничение BitTorrent

Панель: Маршрутизация → Ограничение BitTorrent. ttmenu: пункт 36. Выключено по умолчанию; изменение подтверждается отдельно. Есть два режима: открытые сигнатуры и сигнатуры плюс выбранные TCP/UDP-порты. SSH, UFW и исходящий маршрут не перенастраиваются.

Фильтр в `mangle OUTPUT` выбирает сокеты cgroup службы TrustTunnel. Проверяются открытый handshake BitTorrent/uTP, часть DHT и открытый UDP tracker connect. Служебные ответы с порта endpoint исключены. До изменения выполняется проверка поддержки обеих IP-семей, затем устанавливаются только собственные цепочки. При смене cgroup проверка восстанавливает привязку; статус различает желаемое и проверенное состояние. Счётчик показывает отброшенные пакеты, не число загрузок.

Это пакетные сигнатуры, НЕ полноценное DPI или сборка TCP-потока. MSE/PE, разделённые между пакетами сигнатуры, неизвестные варианты uTP, HTTPS tracker и VPN-в-VPN могут пройти. Выбранные порты могут блокировать легитимные приложения, а торрент может использовать другие порты. Совпадение байтов в обычных данных также может дать ложное срабатывание.

Проверен механизм IPv4/IPv6 в отдельном сетевом namespace: открытые признаки блокируются, тестовые HTTP/TLS/STUN/игровые UDP-пакеты и другой cgroup проходят. Это не испытание всех реальных торрент-клиентов или Android-приложений. Текущий режим WARP-интерфейса не меняется. Для SOCKS/каскада с отдельным процессом полнота фильтрации не квалифицирована: не считайте его гарантированным контролем внешнего прокси.

Если ядро не поддерживает cgroup v2/xt_cgroup/xt_string или IPv6-фильтр, включение прекращается без глобального запрета UDP. При ошибке фонового восстановления VPN не останавливается: режим fail-open, а панель не должна показывать фильтр активным без проверенных правил. После `ufw reload` и перезапуска возможен зазор до фоновой проверки. Удаление панели отключает её фильтр после отдельного подтверждения. Для строгого запрета всех торрентов потребуется иной проверенный анализатор трафика; этот релиз его не подменяет обещаниями.
